## 1. 이미지 저화질 — 원인은 두 개이고, 큰 쪽은 코드에 있다

### 실측

`0.8.0` 매니페스트의 `npc-` 초상 파생본이다.

```
sm  132×192  ×93        md  530×768  ×93
sm  192×192  ×10        md  768×768  ×10
lg  없음
```

### 원인 A — 카지노 로더가 `sm`을 기본으로 쓴다 (주범)

```ts
// temerosa-content.ts:71  파일럿 로더 — md를 쓴다
const variant = asset.variants.find((c) => c.size === "md") ?? asset.variants[0];

// temerosa-content.ts:87  카지노 로더 — sm이 기본이고 md는 상세용으로 분리했다
const small  = asset.variants.find((c) => c.size === "sm") ?? asset.variants[0];
const detail = asset.variants.find((c) => c.size === "md") ?? small;
assets[asset.id] = contentUrl(manifest.version, small.path);      // ← 좌석·손패 전부 이걸 쓴다
```

**좌석 초상과 손패가 전부 132×192를 그린다.** 파일럿 로더는 `md`였는데 카지노 로더에서 내려간 것이다.
손패 카드가 `78×116 CSS px`이면 DPR 3에서 234×348이 필요하다. **132는 절반 남짓이다.**
사용자가 늘 보는 화면이 이쪽이므로 체감 저화질의 대부분이 여기서 나온다.

### 원인 B — `lg` 티어가 없다

상세 모달은 `240×356 CSS px`이라 DPR 3에서 **720×1068**이 필요하다. `md`의 768은 부족하다.
기존 팩(`0.1.0`)에는 `lg`가 있었으나 카지노 팩에는 없다.

### 계약

- **좌석·손패를 `md`로 올린다.** `assets` 맵의 기본 선택을 `sm` → `md`로 되돌린다.
  이것만으로 체감 품질이 가장 크게 오른다. 콘텐츠 재컴파일이 필요 없다.
- **`sm`은 버리지 않는다.** 로비 선택기의 작은 썸네일(35명 격자)에는 `sm`이 맞다.
  용량 때문에 `sm`을 도입한 것이므로 **그 목적에만 남기고**, 게임 화면은 `md`를 쓴다.
  두 맵을 `thumbAssets` / `assets` / `detailAssets` 셋으로 나누는 편이 의도가 드러난다.
- **`lg` 티어를 추가한다.** 세로 상한 1200. **상세 모달 전용이며 지연 로딩**한다.
  전부 미리 받으면 용량이 감당되지 않는다.
- **원본보다 크게 굽지 않는다.** 원본이 작은 인물은 `lg`를 만들지 않고 `md`로 떨어뜨린다.
  없는 화질을 만들어 내면 더 뿌예진다.

### 추가 제안

- **`md` 상향의 용량 영향을 먼저 재라.** 93×4표정을 `sm`에서 `md`로 올리면 초기 전송량이 늘어난다.
  좌석에 앉은 3~4명만 필요하므로 **전량 선로드가 아니라 좌석 확정 후 로드**여야 한다.
  지금 구조가 전량 선로드라면 그것부터 고치는 게 `md` 상향의 전제다.
- `object-position: 50% 18%`가 전 인물 고정값이다. 얼굴 위치는 인물마다 다르므로
  누구는 이마가 잘리고 누구는 턱이 잘린다. **매니페스트에 초점 좌표를 실어 인물별로 지정**하면
  같은 해상도에서도 체감 품질이 크게 오른다. 컴파일 시 자동 추정하지 말고 감사 단계에서 지정한다.
- 확대 표시 요소에 `image-rendering`을 건드리지 않는다. 기본 보간이 가장 낫다.

## 2. 관전 하단 NPC가 말하지 못한다 — 3중으로 막혀 있다

**막혀 있는 게 맞다.** 원인이 하나가 아니다.

```ts
// dialogue.ts
export interface OldMaidSpeechEvent { seatId: OldMaidCpuSeatId; }   // ① 타입이 player를 배제
characters: Record<OldMaidCpuSeatId, string>;                        // ② 스냅숏에 관전자 인물이 없음
const CPU_SEATS = ["cpu-1", "cpu-2", "cpu-3"];                       // ③ 좌석 배열 하드코딩
if (entry.actorId !== "player") …                                    // ④ 가드 네 곳
```

관전 모드에서는 `player` 좌석에도 NPC가 앉는다(`spectatorCharacterId`). 그런데 발화 판정이
좌석 이름만 보고 무조건 뺀다. **유저 시선 하단의 NPC는 구조적으로 절대 말할 수 없다.**

### 계약

- 판단 기준을 **`좌석 이름`이 아니라 `사람이 조종하는가`** 로 바꾼다.
  `mode === "play" && seatId === "player"`일 때만 제외한다.
- `OldMaidSpeechEvent.seatId`를 `OldMaidSeatId`로 넓힌다.
- 스냅숏에 `mode`와 관전자 인물을 싣는다. `characterIdForSeat`가 이미 있으므로 그것을 쓴다.
- 좌석 순회를 `OLD_MAID_SEAT_ORDER` 기반으로 바꾼다. 하드코딩 배열을 지운다.
- 말풍선 위치 규칙이 **`seat-cpu-*`에만 있다.** `old-maid.css:62-63`과 모바일 분기(65행)가 전부 그렇고
  `.seat-player`용 규칙이 없다. 하단 좌석은 기본값 `bottom:calc(100% + 8px)`(좌석 위)로 떨어지는데
  모바일 분기에서는 `top:8px`이라 **초상 안쪽에 겹쳐 뜬다.** 하단 좌석 규칙을 명시적으로 준다.

### 추가 제안

관전 모드는 **네 명이 전부 말한다.** 턴당 발화 1명 예산이 그대로면 각 인물의 등장 빈도가 4분의 1로 준다.
관전은 읽는 것이 목적이므로 **관전 모드에서만 예산을 2명으로 늘린다.**
관전 속도를 `빠르게`로 두면 말풍선 지속 시간도 함께 줄여야 겹치지 않는다.

## 3. 배율 2~5배와 손실 대칭

### 지금 구현된 것

지목한 그 `3배`는 **관전 예측 베팅**의 배당이다. 직접 플레이에는 베팅이 없다.

```ts
// database.ts
if (wallet.balance < input.stake) throw new Error("insufficient_points");
balance: wallet.balance - input.stake                 // 예약 시 판돈 선차감
const settlementCredit = won ? prediction.stake * 4 : 0;   // 적중 시 4배 환급
```

```
판돈 10 · 50 · 200
적중  −10 예약 → +40 환급 = 순 +3배
실패  −10 그대로              = 순 −1배
```

지적한 그대로다. **딸 때는 3배, 잃을 때는 1배.**

관련 상수는 `INITIAL_POINT_BALANCE 0` · `COMPLETION_REWARD 5`(완주, 등수 무관) · `COLLECTION_COST 12`.

### 계약

```
판돈    10 · 50 · 200
배율    2 · 3 · 4 · 5              ← 신규
적중    + 판돈 × 배율
실패    − 판돈 × 배율
```

- **예약액이 판돈이 아니라 `판돈 × 배율`이다.** 그것이 최대 손실 노출액이다.
  잔액 검사(`balance < stake`)와 차감을 전부 이 값으로 바꾼다.
- 적중 시 환급은 `판돈 × 배율 × 2`다. 예약분 회수 + 같은 액수 획득.
- UI는 슬라이더가 아니라 **`2 · 3 · 4 · 5` 버튼 네 개**다. 값이 이산이고 넷뿐이다.
- 잔액으로 감당 못 하는 배율은 **잠근다.** 고른 뒤 거절하지 않는다.
- `PredictionStake`처럼 **배율도 리터럴 유니온**으로 잠근다. `VALID_STAKES`와 같은 방식.
- `SpectatorPrediction`에 `multiplier` 필드를 더한다. 계약 버전을 `spectator-prediction/0.2`로 올리고,
  **필드가 없는 기존 레코드는 `3`으로 읽는다**(현행 순 3배와 일치). 마이그레이션이 필요 없다.
- **전적(A8)과 결과 화면에 배율을 남긴다.** 왜 크게 잃었는지 즉시 보여야 한다.

### 짚어 둘 수치 — 이 변경은 기댓값의 부호를 바꾼다

지금 구조는 4명 중 1명 지목이므로 **찍으면 25%**다. 3:1 배당은 그 25%에 맞춘 공정 배당이다.

```
현행        EV = 0.25 × 3 − 0.75 × 1 = 0            공정
대칭 배율   EV = 배율 × (2p − 1)                     p = 적중률
            → 배율과 무관하게 손익분기 적중률 = 50%
```

**배율은 기댓값을 바꾸지 않는다. 분산만 바꾼다.** 순수한 위험 다이얼이라는 뜻이고, 그 점에서 설계가 깨끗하다.
다만 4지선다에서 손익분기가 50%라는 건 **찍어서는 반드시 잃는다**는 뜻이다.

그게 나쁜 게 아니다 — **텔 읽기가 돈이 되는 유일한 구조**다. 25%를 50% 위로 끌어올릴 수 있는 사람만
이익을 낸다. 심리 코어와 대사·표정이 그제서야 경제적 의미를 갖는다. 무료 테이블이 있으니 바닥도 안전하다.

문제는 4지선다에서 50%가 **꽤 가혹하다**는 것뿐이다. 그래서:

### 추가 제안 — 2인 지목 베팅

같은 엔진에 지목 인원 수만 더한다.

```
1인 지목   기본 적중률 25%   손익분기 50%   고위험
2인 지목   기본 적중률 50%   손익분기 50%   찍어도 본전, 읽으면 이득
```

2인 지목은 **찍기만 해도 손익분기**라 읽는 실력이 조금만 붙어도 이익이 난다.
입문자가 앉을 자리가 생기고, 1인 지목은 자신 있는 판에만 거는 고배당 자리로 남는다.
배율 다이얼이 그제서야 의미를 갖는다 — 지금은 어느 배율을 골라도 장기적으로 같은 속도로 잃는다.

구현은 `predictedCharacterId: string` → `predictedCharacterIds: readonly string[]`(길이 1 또는 2)이고,
정산은 `ids.includes(winningCharacterId)`다. 그 이상 복잡해지지 않는다.

## 4. 로비에서 좌석이 갱신되지 않는다

`opponentIds`(로컬 상태)는 정상 갱신된다. 그런데 좌석 패널이 그것을 보지 않는다.

```ts
// old-maid-screen.tsx:52   선택은 여기에 쌓이는데
const [opponentIds, setOpponentIds] = useState(() => Object.values(state.characters));

// old-maid-screen.tsx:269  좌석은 여기를 그린다
const character = characters.get(state.characters[seatId]);
```

`state.characters`는 `start` 액션 전까지 바뀌지 않는다.

→ 선택을 바꿔도 **상단 좌석은 처음 들어왔을 때 값 그대로**다. 정확히 보고된 증상이다.

### 계약

- `status === "ready"`일 때 좌석 패널이 **`opponentIds`를 미리보기로** 그린다.
  상태를 바꾸지 않는다. 렌더 시점의 대체다.
- 선택 순서가 좌석 순서(`cpu-1 · cpu-2 · cpu-3`, 관전은 + 하단)임을 화면에서 알 수 있게 한다.
  지금은 누가 어디에 앉는지 고르는 동안 알 수 없다.

## 5. 결과 화면 버튼 문구

```
같은 판 다시 하기      유지
새 상대와 섞기    →   상대 다시 고르기
```

두 버튼은 기능이 실제로 다르다. 하나는 같은 시드 재시작이고 하나는 **로비로 돌아가 상대를 다시 고르는 것**이다.
문구가 그 차이를 말해야 한다. `섞기`는 카드를 섞는다는 뜻으로 오독된다.

## 6. 일시정지 · 진행 방식

기능이 없다. API 응답을 기다리며 하는 게임이므로 **자리를 비우는 것이 정상 사용 패턴**이다.

### 선례가 이미 있다 — 새로 설계하지 않는다

럭키 더비가 같은 문제를 이미 풀었다.

```ts
// derby-bakeoff-screen.tsx:73
const onVisibility = () => { if (document.hidden) runtimeRef.current?.pause(); else runtimeRef.current?.resume(); };
document.addEventListener("visibilitychange", onVisibility);

// runtime/shared.ts:49
while (isPaused() && !isStopped()) await new Promise((r) => window.setTimeout(r, 50));
```

**같은 형태를 도둑잡기에 옮긴다.** `isPaused()` 술어를 진행 루프에 끼우는 방식이고, 상태를 건드리지 않는다.
어댑터 넷이 전부 이 패턴을 공유하므로 검증도 끝나 있다.

### 계약

- 헤더에 **일시정지 / 계속** 버튼을 둔다.
- 정지 중에는 **NPC 자동 진행 타이머를 전부 멈춘다.** 상태는 그대로 두고 화면도 그대로 보인다.
  손패와 표정을 읽을 시간이 된다.
- **탭이 백그라운드로 가면 자동으로 일시정지한다**(`visibilitychange`).
  채팅하러 갔다 돌아왔을 때 판이 끝나 있는 일이 없어야 한다.
- 타이밍은 상태나 결과 해시에 넣지 않는다. 순수 표현 계층이다.

### 추가 제안 — 진행 방식 선택

일시정지만으로는 *"NPC가 알아서 진행해 버리는 것"* 자체는 해결되지 않는다.
**진행 방식을 고르게 한다.**

```
자동 (기본)   지금과 같다
수동          NPC 차례마다 `다음` 을 눌러야 진행한다
```

수동은 한 수씩 읽고 싶은 사람과, 자리를 자주 비우는 사람 모두를 만족시킨다.
설정은 화면 로컬이며 저장하지 않아도 된다.

## 7. 시작 · 순위 · 패배 대사

**두 겹으로 막혀 있다.**

```ts
// dialogue.ts — 이 셋이 전부 침묵 구역이다
status === "ready" || status === "dealing" || status === "complete"
```

시작 대사가 나와야 할 `ready`/`dealing`과 승패 대사가 나와야 할 `complete`가 전부 막혀 있고,
`OldMaidLineEvent`에 해당 상황이 없다.

### 계약

**신규 이벤트 5종**

```ts
"table-open"    배분 직후, 좌석 전원이 한 마디
"finish-1st"    1등으로 손을 비움
"finish-2nd"    2등
"finish-3rd"    3등
"defeat"        조커를 떠안고 패배
```

**침묵 규칙 개정**

- `dealing` 종료 시점에 `table-open`을 허용한다.
- `complete` 진입 시 `finish-*`·`defeat`를 허용한다.
- **최종 2인 구간의 침묵은 유지한다.** 조커가 확정되기 직전의 정적이 결과 대사를 무겁게 만든다.
  침묵을 푸는 것은 결과가 나온 **뒤**다.

**기존 `emptied`와의 관계**

`emptied`는 남긴다. `finish-*`가 있으면 그것을 쓰고, 없으면 `emptied`로 떨어진다.
**이것은 폴백이 아니라 계층이다** — 같은 인물의 같은 사건에 대한 더 구체적인 줄이 있으면 그것을 쓴다.

**연출**

- `table-open`은 **전원 동시에 띄우지 않는다.** 좌석 순서로 0.4초 간격을 둔다. 겹치면 아무것도 안 읽힌다.
- `defeat`는 `despairPortrait`와 함께 띄운다. 자산이 이미 있다.
- 결과 화면에서 순위표와 함께 보이게 한다.

### 집필량

**35명**(기존 9 + 신규 26) × **5상황** = **175줄**이 필요하다.

| 차수 | 상황 | 줄 수 |
|---|---|---|
| 1차 | `table-open` · `finish-1st` · `defeat` | **105** |
| 2차 | `finish-2nd` · `finish-3rd` | 70 |

1차만으로도 시작·승리·패배가 전부 채워진다. 2·3등은 그때까지 `emptied`가 맡는다.

**집필은 이 문서의 범위가 아니다.** 대사집에 추가되며, 배선은 SPEC-A19와 같은 규칙을 따른다 —
**문안을 코드에서 고치지 않는다.**

## 8. 추가 제안 — 조사 중 발견한 것

### 8.1 인물 정보를 볼 방법이 없다

좌석 후보가 **35명**으로 늘었는데 이름만 보인다. 누가 누군지 알 방법이 없다.

→ 로비 선택기에서 초상을 **길게 누르거나 우클릭하면 한 줄 소개**를 띄운다.
명부 문서의 `도출한 한 줄`이 그대로 쓰인다. 도감(SPEC-A14)과 같은 데이터를 공유한다.

### 8.2 손패 재배열을 아무도 모른다

심리전의 핵심 수단인데 **발견 가능성이 없다.** 드래그할 수 있다는 표시가 없다.

→ 첫 판의 첫 자기 차례에 한 번만 힌트를 띄운다. 이후에는 띄우지 않는다.

### 8.3 모바일 말풍선이 겹칠 수 있다

좌석 셋이 가로로 좁게 붙어 있다. 관전 모드에서 예산을 늘리면 더 겹친다.

→ 모바일에서는 말풍선을 좌석 위가 아니라 **중앙 상단 한 곳에 이름과 함께** 띄우는 편이 읽힌다.

### 8.4 관전 결과 화면 문구

플레이어가 참여하지 않은 판인데 `플레이어는 n번째로 손을 비웠습니다`가 나오지 않는지 확인한다.

### 8.5 같은 인물이 두 좌석에 앉지 않는지

35명 중 셋을 고르는 구조라 중복 선택이 막혀 있어야 한다. 검증한다.

## 9. 테스트 관문

1. `lg` 변형이 원본보다 크지 않다. 원본이 작은 인물은 `lg`가 없다.
2. 좌석·손패가 `md`를, 로비 썸네일이 `sm`을, 상세 모달만 `lg`를 요청한다.
2-1. 좌석에 앉지 않은 인물의 표정 4종을 게임 시작 시 받지 않는다.
3. **관전 모드에서 네 좌석 전부 발화 기록이 남는다.** 1,000시드에서 하단 좌석 발화 0건이면 실패다.
4. 직접 플레이에서는 `player` 좌석이 절대 발화하지 않는다.
5. 배율 2·3·4·5 전부에서 적중 순이익과 실패 손실의 절댓값이 같다.
6. 예약 시 `판돈 × 배율`이 차감되고, 잔액이 그보다 작으면 그 배율이 잠긴다.
6-1. `multiplier` 없는 기존 예약 레코드가 `3`으로 읽히고 정산 결과가 현행과 같다.
6-2. 무효화 환불액이 예약액(`판돈 × 배율`)과 정확히 같다. 판돈만 돌려주면 손실이다.
7. 로비에서 상대를 바꾸면 좌석 미리보기가 즉시 따라간다.
8. 일시정지 중 NPC가 진행하지 않는다. 탭 전환에서도 같다.
9. 수동 진행에서 `다음`을 누르기 전까지 상태가 변하지 않는다.
10. `table-open`이 배분 직후 좌석 순서로 뜨고 겹치지 않는다.
11. 최종 2인 구간이 여전히 침묵이다.
12. `finish-*`가 없는 인물은 `emptied`로 떨어지고, 둘 다 없으면 침묵한다.
13. 판정 불변 — 대사·타이밍·배율 UI가 `resultHash`를 바꾸지 않는다.
14. 10,000시드 완주가 그대로 통과한다.
