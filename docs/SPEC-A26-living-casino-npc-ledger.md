> 상태: v1.0 구현 계약 (2026-07-26). 오너 승인 — **A안(비접촉 경제) · 방안 1(24시간)**.

> 관련: [SPEC-A23](./SPEC-A23-common-game-wager.md)(공용 판돈) · [백로그 RECORDED 라이브 오즈](./BACKLOG.md) ·

## 0. 한 줄

**NPC 35명이 24시간 카지노에서 도박하고, 그 잔고를 모든 플레이어가 똑같이 본다. 서버는 쓰지 않는다.**

잔고가 순수 함수이기 때문이다. 유저 1의 박니은과 유저 2의 박니은이 4,120 P로 일치하는 이유는
서버가 알려줘서가 아니라 **둘 다 같은 식을 계산해서**다.

## 1. 오너 결정

| 결정 | 내용 |
|---|---|
| **A안** | NPC 잔고는 **표시용**이다. 유저가 NPC를 이겨도 그 포인트를 가져오지 않는다 |
| **방안 1** | NPC는 유저가 접속하지 않은 동안에도 활동한다 |
| **정본 필터 없음** | 카지노는 **스핀오프 세계관**이다. 원작에서 한자리에 모일 수 없는 인물도 여기서는 모인다 |

### 스핀오프 선언을 문서로 남기는 이유

[좌석 대사집](./TEMEROSA-OLD-MAID-DIALOGUE.md) 4절 **정본 보호 규칙 3**은 *박니은을 자리에서 움직이지
않는다*고 못박았고, [의례 대사집](./TEMEROSA-OLD-MAID-CEREMONY-DIALOGUE.md)의 박니은 다섯 줄은 전부
그 규칙을 지켜 잔류로 썼다. 이 명세는 그 규칙과 **의도적으로 다른 층**에 있다.

```
게임 테이블 안   정본 규칙 유효. 박니은은 손을 비워도 일어나지 않는다
카지노 원장      스핀오프 프레임. 인물 제한 없음
```

두 층은 충돌하지 않는다. 원장은 **누가 어디서 얼마를 잃었나**를 말할 뿐 좌석 대사를 만들지 않는다.
이 구분을 지우고 원장이 대사를 생성하기 시작하면 정본 보호 규칙과 정면으로 충돌한다. **그 선을 넘지 않는다.**

## 2. 왜 서버가 필요 없나

```
NPC 잔고(npcId, UTC 시각) = 순수 함수
```

- 모든 클라이언트가 같은 입력에 같은 출력을 낸다 → 유저 간 일치가 **자동**
- 개점일부터의 과거를 언제든 다시 계산한다 → **24시간 도는 프로세스가 없어도 24시간 돈 것처럼 보인다**
- 오프라인에서도 작동한다
- 서버 비용 0, 네트워크 왕복 0

**방안 2(유저 활동 시에만)가 오히려 더 어렵다.** "활동 중"을 정의해야 하고, 유저마다 활동 시각이 달라
잔고가 어긋나며, 그 어긋남을 맞추려면 결국 서버가 필요해진다. 방안 1이 더 싸고 더 쉽다.

시계 조작은 A안에서 착취 경로가 아니다. 기기 시간을 앞으로 돌리면 **자기 화면의 NPC만 미래로 가고
아무 이득이 없다.** 3절의 시계 정책으로 정확도만 맞춘다.

## 3. 시각

- 입력은 **UTC epoch 분**이다. 로컬 시각을 쓰면 시차가 다른 두 유저가 다른 숫자를 본다.
- 개점 기준시(`epochUtcDay`)를 계약에 고정한다. 이 값이 바뀌면 모든 역사가 바뀐다.
- **기기 시계를 그대로 믿지 않는다.** 앱은 이미 콘텐츠 매니페스트를 `fetch`하므로, 그 응답의
  `Date` 헤더를 읽어 기기 시계와의 오차를 한 번 보정한다. **추가 요청 0회.**
- 헤더를 못 읽으면 기기 시계로 떨어진다. A안이라 손해가 없다.

```ts
export interface CasinoClock { utcMinute(): number; }
export function clockFromResponse(response: Response, performanceNow: number): CasinoClock;
export function deviceClock(): CasinoClock;
```

순수 계층은 시계를 **주입받는다.** 원장 함수 안에서 `Date.now()`를 부르지 않는다. 테스트가 시각을
고정할 수 있어야 하고, 그것이 결정론의 실제 의미다.

## 4. 원장 모델

### 4.1 평균회귀가 필수인 이유

자유 랜덤워크로 두면 **한 달 뒤 상위 NPC가 10억 P가 되고 순위표가 영구히 무의미해진다.**
유저가 1위를 노려볼 수 있는 천장이 유지돼야 한다.

이산 오른슈타인-울렌벡을 쓴다.

```
delta_d = θ · (μ − balance_{d−1}) + σ · μ · noise_d
balance_d = clamp(balance_{d−1} + delta_d, 0, ∞)
```

| 기호 | 뜻 | 출처 |
|---|---|---|
| `μ` | 그 인물이 머무는 잔고 수준 | **집필**한다. 인물 해석에서 나온다 |
| `σ` | 변동폭 (μ 대비 비율) | `riskAppetite` |
| `θ` | 되돌아오는 힘 | `consistency` |

정상 상태 표준편차는 대략 `σ·μ / √(2θ − θ²)`다. `θ=0.10 · σ=0.15`면 약 `0.34μ`이므로 잔고는
대략 `μ ± 0.7μ` 안에서 논다. `μ=5,000`이면 1,500~8,500 사이다. **유저가 도달 가능한 범위다.**

`clamp` 하한 0은 순수 OU를 살짝 깨지만, 파산한 NPC가 마이너스로 가는 것보다 낫다.
잔고 0에 닿은 NPC는 다음 날 `θ·μ`만큼 회복한다 — **무료 테이블에서 다시 벌어 온 것**으로 읽힌다.

### 4.2 하루는 세션의 합이다

잔고만 있으면 숫자판이지 카지노가 아니다. **하루치를 세션 목록으로 만들고, 그 합이 곧 일일 변동**이다.
한 함수가 두 곳에 쓰인다 — 순위표의 숫자와, 티커의 "카미유 · 3분 전 · 슬롯 −50 P".

```ts
export interface NpcSession {
  minuteOfDay: number;   // 0..1439, UTC
  tableId: string;       // "temerosa-old-maid" | "temerosa-match-pairs" | "temerosa-slot" | ...
  stake: number;         // 10 | 50 | 200
  delta: number;         // 정수. 합이 그 날의 일일 변동과 정확히 같아야 한다
}

export function npcDaySessions(profile: NpcGamblingProfile, dayIndex: number, openingBalance: number): readonly NpcSession[];
```

- 세션 수는 `sessionsPerDay` 범위에서 시드로 뽑는다. `consistency`가 높을수록 편차가 작다.
- 세션 시각은 하루에 고르게 흩되 인물별 활동 시간대 가중을 준다(야행성·주간형).
- **세션 delta의 합을 4.1의 일일 변동에 정확히 맞춘다.** 마지막 세션에서 반올림 오차를 흡수한다.
  이 규칙이 없으면 티커의 합과 순위표의 숫자가 어긋난다. 유저는 그걸 알아챈다.

### 4.3 잔고 조회

```ts
export function npcBalanceAt(profile: NpcGamblingProfile, clock: CasinoClock, contract: NpcLedgerContract):
  { balance: number; today: readonly NpcSession[]; dayIndex: number };
```

개점일부터 어제까지를 순차 누적하고, 오늘은 현재 분까지의 세션만 더한다.

**비용**: 하루당 산술 몇 번 × 경과 일수 × 35명. 1년이 지나도 35 × 365 ≈ 13,000회로 밀리초 단위다.
그래도 **어제까지의 누적은 `localStorage`에 캐시**한다. 캐시 키에 계약 버전과 일 인덱스를 넣는다.

```
npc-ledger/0.1:<npcId>:<dayIndex>  ->  balance
```

캐시가 없거나 계약이 바뀌면 전량 재계산한다. 캐시는 **최적화일 뿐 진실이 아니다.**

## 5. 인물 → 도박 성향

새 능력치를 발명하지 않는다. 기존 4축 중 셋만 쓰고, 나머지 하나는 **의미가 없으므로 쓰지 않는다.**

```
riskAppetite   → σ (변동폭).  판돈 크기와 잔고 요동
consistency    → θ (되돌아오는 힘) 와 세션 수 편차
readAccuracy   → 세션 승률 편향.  잘 읽는 인물이 조금 더 자주 이긴다
deceptionBias  → 쓰지 않는다.  잔고 시뮬레이션에 대응물이 없다
signalAttention · signalTrust → 쓰지 않는다
```

**`readAccuracy`로 인한 상방 압력은 `θ`가 흡수한다.** 잘 읽는 인물은 `μ`가 높은 게 아니라
`μ`에 더 빨리 복귀한다. `μ`는 어디까지나 집필값이다.

### 5.1 `μ`는 집필한다

이게 이 명세에서 유일하게 창작이 필요한 값이고, **순위표를 이야기로 읽히게 만드는 핵심**이다.
[명부](./TEMEROSA-CASINO-NPC-ROSTER.md)의 `도출한 한 줄`이 그대로 근거가 된다.

```
카트린카   높다.  백 번 살려 주고 한 번도 공짜로 해준 적 없는 유료 치료사
레이븐     높다.  어떤 상황에서도 정중한 계산
브체       낮다.  밀린 집세
모르시사   낮다.  가장 약한 정예
튜밋튜     낮다.  신인
레빌로트   중간이지만 σ가 크다.  초강력 운을 자랑하는 만큼 요동친다
트레버     중간이고 σ가 작다.  분수껏
```

**순위표가 이야기로 읽힌다.** "브체는 왜 항상 바닥이지" → 그게 그 인물이다.
추가 집필은 35줄의 숫자 하나씩이고, 대사집처럼 해석에서 도출한다.

전체 35명의 `μ · σ · θ · 활동 시간대 · 자주 가는 테이블`은 별도 데이터 파일에 둔다.
**코드에 흩지 않는다.** 대사 문안을 코드에서 고치지 않는 것과 같은 규율이다.

## 6. 순위표

```
NPC 35명    클라이언트가 계산한다.        네트워크 0
유저 본인   IndexedDB 지갑에서 읽는다.     네트워크 0
다른 유저   1단계에서는 없다.             7절 참조
```

정렬은 셋을 합쳐서 한다. **1~3단계에서 순위표는 서버를 전혀 쓰지 않는다.**

- 동점은 `npcId` 사전순으로 깬다. 정렬이 흔들리면 안 된다.
- 유저 본인 행은 순위 밖이어도 항상 보인다(고정 행).
- 표시 단위는 P, `tabular-nums`.

## 7. 나중에 서버가 필요한 곳 — NPC가 아니다

**다른 유저의 점수만이 진짜 서버를 요구한다.** 그리고 여기엔 이 프로젝트가 이미 기록한 원칙이 걸린다.

> 서버 검증 없는 전역 순위표를 붙이지 않는다 — [짝맞추기 검토](./MATCH-PAIRS-AND-ROADMAP-REVIEW-2026-07-26.md) §6

지갑이 IndexedDB에 있으니 누구나 자기 점수를 고칠 수 있다. 그 상태의 순위표는 순위표가 아니다.

### 우리는 이걸 풀 수 있는 형태를 이미 갖고 있다

```
ActionReceipt WAL  +  결정론 코어  +  resultHash
```

클라이언트가 행동 로그를 올리고 Cloud Function이 **같은 순수 코어로 재생해 해시를 대조**한다.
경계 검사가 캐비닛 코어에 React·DOM을 금지해 왔기 때문에 그 코어가 Node에서 그대로 돈다.
도둑잡기 한 판은 카드 25장·40턴이라 재생 비용이 무시할 수준이다.

전량 검증이 부담되면 **순위표 상위권만** 검증한다.

### 그때의 지연 대책

```
게임 중     네트워크 호출 0회.  지금과 동일하게 완전 로컬
판 종료     쓰기 1회.           턴마다가 아니라 판마다
순위표      집계 문서 1개 읽기.  컬렉션을 직접 읽으면 접속당 수십~수백 읽기가 난다
지갑        로컬이 게임의 진실.  서버 사본은 표시·순위 전용
로그인      익명 인증 먼저.      원하면 나중에 계정으로 승격
오프라인    Firestore 오프라인 지속성 + 쓰기 큐
```

**게임 루프를 네트워크에 올리지 않는다. 결과만 동기화한다.** 이 한 줄이 지연 대책의 전부다.

## 8. 절대 어기지 않을 것

1. **원장은 게임 판정에 영향을 주지 않는다.** 이 명세를 통째로 지워도 모든 게임의 동일 시드
   `resultHash`가 같아야 한다.
2. **NPC 잔고는 유저 지갑과 닿지 않는다**(A안). 두 값은 같은 트랜잭션에 들어가지 않는다.
3. **순수 계층에서 `Date.now()`·`Math.random()`을 부르지 않는다.** 시계는 주입한다.
4. **원장이 대사를 생성하지 않는다.** 1절의 두 층 구분을 지운다는 뜻이다.
5. **파라미터는 배포되면 동결된다.** 9절 참조.

## 9. 파라미터 동결과 재기준

가장 위험한 실수는 이것이다.

> 모델 상수를 나중에 조금 고쳤더니 **모든 NPC의 과거가 통째로 바뀐다.**
> 어제 4,120 P였던 박니은이 오늘 8,700 P가 되고, 유저는 자기가 뭘 본 건지 알 수 없게 된다.

따라서:

- `μ · σ · θ · epochUtcDay · 세션 규칙`은 **배포된 순간 동결**된다.
- 조정이 필요하면 **재기준(rebase)** 한다. 새 계약 버전(`npc-ledger/0.2`)과 새 기준일을 두고,
  기준일의 시작 잔고를 **구 모델이 그 날 산출한 값으로 고정**한 뒤 새 파라미터로 이어 간다.
- 재기준은 과거를 다시 쓰지 않는다. **꺾이되 끊기지 않는다.**

## 10. 화면

### 10.1 명예의 전당 (플로어)

플로어에 순위 패널을 둔다. 상위 N명 + 유저 본인 고정 행.
`.ca-tableau` 위에 `.ca-brackets`, 숫자는 `NumberTicker`로 굴린다.

### 10.2 활동 티커

플로어 하단 또는 관전석 입구에 최근 세션이 흐른다.

```
카미유 · 3분 전 · 슬롯 · −50 P
레이븐 · 8분 전 · 도둑잡기 · +150 P
```

세션은 4.2에서 이미 계산돼 있으므로 **추가 비용이 없다.**
`.ca-live` 점등과 오름/내림 색(`--ca-rising` / `--ca-falling`)을 쓴다.

### 10.3 접근성

- 티커는 `aria-live`를 걸지 않는다. 계속 흐르는 장식이 스크린리더를 점거하면 안 된다.
- 순위표는 `<table>`로 마크업하고 순위·이름·잔고를 헤더로 준다.
- `prefers-reduced-motion`에서 티커는 흐르지 않고 최신 3건만 정적으로 보인다.

## 11. 이미 열려 있는 두 항목이 여기서 닫힌다

**관전석** — 플로어가 「준비 중」으로 약속만 하고 내용이 없었다. 원장이 생기면 관전석이 실제가 된다.
지금 카미유와 레이븐이 붙고 있는 판을 들어가서 본다. 그 판은 `(참가자, 시각 슬롯, 시드)`의
**순수 함수라 그대로 재생된다.** 서버 중계가 필요 없다.

**라이브 오즈** — 백로그에 기록하며 남긴 미결 질문이 *"손패가 공개된 관전에서 무엇이 요동치는가"*였다.
답이 여기 있다. **조커 확률이 아니라 시장이 흔들린다.** NPC 잔고와 판돈이 요동친다.

둘 다 이 명세가 착지한 뒤에 착수한다. 지금 같이 만들지 않는다.

## 12. 단계와 관문

```
1. 순수 원장 코어        npcDaySessions · npcBalanceAt · 시계 주입 · 유닛 테스트
2. 순위표 + 티커 표시     NPC만. 유저는 자기 자신만 로컬로 끼워 넣음
3. ── 재미 관문 ──       여기서 오너가 판정한다
4. 익명 인증 + 유저 순위 동기화
5. 재생 검증 (Cloud Function)
6. 관전석을 실제 진행 중인 판에 연결
7. 라이브 오즈를 NPC 시장에 연결
```

**3번이 관문인 것이 이 계획의 핵심이다.** 1·2는 서버도 계정도 없이 끝나고, 그 상태에서
*"NPC 순위표가 재미있는가"* 를 실제로 잴 수 있다. **재미없으면 계정 시스템을 아예 만들지 않는다.**

## 13. 테스트 관문

1. 같은 `(npcId, dayIndex)`가 언제 어디서 계산해도 같은 값을 낸다.
2. 세션 `delta`의 합이 그 날의 일일 변동과 **정확히** 같다(반올림 오차 0).
3. 10,000일을 굴려도 모든 NPC 잔고가 `[0, 20μ]` 안에 머문다. 발산하지 않는다.
4. 잔고가 0에 닿아도 마이너스로 내려가지 않고 다음 날 회복한다.
5. 순수 계층이 `Date.now()`·`Math.random()`을 부르지 않는다(정적 검사).
6. 캐시를 전부 지워도 같은 잔고가 나온다. **캐시는 진실이 아니다.**
7. 시계를 하루 앞으로 밀면 하루치가 더해지고, 되돌리면 원래 값으로 돌아온다.
8. 원장을 통째로 비활성화해도 모든 게임의 동일 시드 `resultHash`가 같다.
9. 초기 JS gzip 예산을 넘지 않는다. 원장은 플로어 청크로 지연 로딩한다.
10. `μ` 순서가 인물 해석과 어긋나지 않는다(집필값 회귀 테스트).
