# 카지노 성능 수리 — 2026-09-16

## 원인

조사 기준 HEAD: `efc2b25`. NPC 103명 자체보다 역사 재생 방식이 병목이었다.

- `completedDayBalances()`가 기본적으로 개장일부터 요청일까지 순회했다.
- 전체 일일 계획 캐시는 16개였다. 조회 기간이 이를 넘으면 앞쪽 날짜 재생이 뒤쪽 캐시까지 밀어내는 순환 퇴거가 발생했다.
- 플로어의 라이브 테이프는 매초 이 경로를 호출했다.
- 도둑잡기/짝맞추기/인디언 포커/파이브 카드 드로는 상대 이용 가능 여부를 대국 중에도 매초 조회했다.
- 개인 원장의 체크포인트 최적화는 재실 상태/테이프의 별도 재생 경로에는 적용되지 않았다.
- 관전 재생의 `setTimeout(0)`는 시작만 미룰 뿐, 실제 리듀서 계산을 메인 스레드에서 분리하지 않았다.

### 동일 PC, Node 계측

시각을 주입하여 같은 103명으로 비교했다. 브라우저 전체 로딩 시간과는 다른 수치다.

| 경로 | 수정 전 2026-09-16 정오 | 캐시 수리 후 |
|---|---:|---:|
| 재실 상태 첫 호출 | 16,089ms | 16,571ms |
| 재실 상태 반복 호출 | 14,278ms | 6.84ms |
| 라이브 테이프 반복 호출 | 13,869ms | 5.53ms |

정오 테이프 결과는 빈 배열이었다. 위 수치는 역사 재생 병목 제거를 보여주지만, 활발한 시간대의 최대 이벤트 렌더링 비용을 대표하지 않는다. 최초 cold 재생 자체는 여전히 비용이 있다.

## 수정

1. 엔진에 소형 종가 체크포인트 캐시 추가: 계약별 최대 8개 입력 분기 × 64일. 전체 대국 계획은 기존 16개 한도를 유지한다. 명시적 체크포인트·프로필·계약 값이 다르면 별도 계산하며 날짜를 되돌릴 때 미래 종가를 쓰지 않는다.
2. 재실 구간은 최근 2개 계획에 대해서만 재사용한다.
3. 네 게임 모두 준비/완료 화면에서만 상대 일정을 조회한다. 준비 화면은 5초 주기, 비활성 탭에서는 조회하지 않는다. 파이브 카드 연속 대국의 판 사이에도 조회를 멈춘다.
4. 플로어/상대 일정/하우스 및 NPC 잔고 조회를 단일 `casino-runtime.worker`로 옮겼다. 화면 render에서 경제를 직접 재생하지 않는다.
5. 원장은 10초 단위 요약, 재실 상태와 테이프는 같은 worker의 계획 캐시를 공유한다. 로컬 거래 내용이 바뀌면 개인 가지 요약을 무효화한다.
6. 개인 원장 첫 복구에 로컬 거래가 없다면 완료한 날짜의 공개 종가를 단계적으로 채워 후속 테이프의 중복 전체 재생을 줄인다. 저장 체크포인트에서 시작한 복구는 이 priming을 하지 않는다(과거 전체를 다시 읽는 회귀 방지).
7. 저장 체크포인트는 메인 스레드의 localStorage와 worker 사이에서 전달한다. worker에는 메모리 저장 어댑터를 사용한다. 저장 실패 시에도 메모리 캐시는 유지된다.
8. 전체 주간 활동을 매초 화면으로 복사하지 않는다. 요약·최근 행만 전달하며 NPC 상세 전적은 요청했을 때 비동기로 가져온다.
9. 관전 리듀서는 별도 `casino-side-market-replay.worker`에서 실행한다. 단일 worker/유계 대기 큐/취소/오류/120초 제한을 적용했다. 경제 worker도 유계 큐와 제한 시간을 가진다. Worker 실패 시 메인 스레드 전체 재생으로 fallback하지 않는다.
10. 최초 경제 복구 중에도 게임 진입 버튼을 제공한다. Worker는 요청이 있을 때만 일하며 자체 상시 타이머는 없다.

경제 상수·시드·계약 버전·기준일·게임 판정·플레이어 지갑 저장 형식은 변경하지 않았다. NPC 축소나 잔고 초기화도 하지 않았다.

## 남는 한계 / 후속 작업

- 새 브라우저의 최초 역사 복구는 즉시 완료되지 않는다. 이번 수정은 이를 화면 스레드 밖으로 옮기고 반복 전체 재생을 제거했다. 게임의 상대 선택이나 베팅 잔고 확인은 최초 복구 결과를 기다릴 수 있다.
- 개인 원장 체크포인트는 저장하지만 공개 재실 엔진의 종가 캐시는 worker 메모리 범위다. 브라우저를 완전히 새로 열면 공개 역사 복구 비용이 다시 발생할 수 있다. 이를 더 줄이려면 계약별 검증된 공개 종가/하우스 스냅샷을 함께 저장·복원하는 별도 보강이 필요하다.
- 실제 103명의 365일 cold 벤치마크와 실제 저사양 휴대전화 장기 사용은 이번에 수행하지 않았다. 장기 cold 측정은 `CASINO_HISTORY_BENCHMARK=1`, `CASINO_HISTORY_BENCHMARK_DAYS=365` opt-in 테스트로 남겼다.
- 기존 `days=0` NPC 상세 전적이 개인 원장의 최근 활동 보관 범위를 따르는 동작은 바꾸지 않았다.
- 이번 작업에서는 커밋·푸시·배포하지 않았다.
